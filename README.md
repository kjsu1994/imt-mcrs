# MCSR · Orbital Network Lab

목표는 **MCSR 알고리즘 자체를 구현하고, 그 선택·복구 과정을 3D에서 관찰·분석·검증하는 것**입니다. 논문의 실험 수치를 복제하는 것이 완료 조건은 아닙니다. React + TypeScript + Vite + CesiumJS로 구성하며 서버·DB·계정·지도 토큰 없이 동작합니다.

현재는 **16기 이하 정밀 검증 모드와 72기·1,584기 확장 모드**를 지원합니다. 두 모드 모두 고정 SRD·DS, 영역 내부 경로와 경계 연결, ISL을 따라 전달되는 CSIB·ACK·재전송, D/A/J 선택·예비 전환·재계산을 실행합니다. 정밀 모드는 독립적인 전수 탐색과 후보 집합을 비교합니다. 확장 모드는 탐색량을 제한하므로 모든 우세 경로나 전역 최적 경로를 보장하지 않습니다. 비교용 BFS·수동 후보·자동 우세 경로도 유지합니다.

| 기능 | 현재 상태 |
|---|---|
| GS·UT 우클릭 배치, 지상 접속·핸드오버, BFS·MCSR 종단 통신 | 구현 |
| 독립 논리 시계, 장애 감지, 상태·속성 입력 버전 | 구현 |
| 경로 독립 검증, 후보 비교·이유, 예비 전환·재계산 구분 | 구현 |
| JSON 가져오기·저장, Worker/CLI/탐색에서 설정 복원, 3D 후보 검토 | 구현 |
| 16기 이하 자동 우세 경로 집합·탐색 요약·계산 한도 | 구현 |
| 고정 SRD·DS·CSIB, 영역 내/간 경로 연결 | 정밀·확장 모드 구현 |
| 72기·1,584기 제한 후보 탐색·변경분 전달 | 구현 |

| 실제 제어 패킷 전송·실측 지터·패킷 큐 | 후속 모델 |

정밀 모드의 완료 조건은 작은 그래프 기준 결과와의 후보 집합 일치, 서비스별 선택의 정확성, 순환 없는 종단 경로, SRD 내부·경계·SRD 간 장애의 복구 동작, 동일 입력의 재현성, 그리고 화면·판단 기록의 일치입니다. 확장 모드는 경로·속성·서비스 조건의 독립 검증, 장애 복구와 입력 재현성, 제한 정책·제외 수의 공개를 완료 기준으로 삼습니다. BFS의 테스트 통과나 표시 FPS는 MCSR 정확성의 증거가 아닙니다.

## 실행

Node.js 24와 npm을 사용합니다. PowerShell 실행 정책 문제를 피하려면 `npm.cmd`를 사용하세요.

```powershell
npm.cmd ci
npm.cmd run dev
```

개발 서버: http://127.0.0.1:5173 . 설치에는 인터넷이 필요하지만 설치와 빌드 후 앱 실행에는 필요하지 않습니다.

```powershell
npm.cmd run typecheck
npm.cmd test
npm.cmd run build
npm.cmd run preview
npm.cmd run test:browser
```

브라우저 테스트는 Windows에서 설치된 Microsoft Edge, Linux CI에서 Playwright Chromium을 사용합니다. `dist/`를 정적 HTTP 서버로 제공하면 배포할 수 있습니다. `file://`로 직접 여는 방식은 지원하지 않습니다. Cesium 정적 파일은 dev/build 전에 로컬로 복사합니다. 클라우드 드라이브에서는 npm 설치·복사가 느릴 수 있습니다.

## 조작

- 지구본 드래그로 극점 제한 없이 상하좌우 연속 회전, 휠·오른쪽 드래그로 확대/축소합니다. 일반 보기의 이동·기울이기는 제한하고, 위성 추적 해제 시에도 지구 중심을 유지합니다. 확대 범위는 지표 기준 약 250~50,000km입니다. 지표까지 거리가 가까울수록 드래그 회전 폭도 줄어듭니다.
- 위성 클릭 또는 위성 선택 목록으로 정보 확인. 위성 추적 / 전체 보기로 카메라 전환.
- 출발·도착 위성을 고르면 초록색 경로와 노란색 패킷 흐름을 표시합니다. 동일 노드는 전송하지 않고, 연결되지 않으면 경로 없음으로 표시합니다.
- 선택 위성을 통신 출발·도착 노드로 지정할 수 있습니다. 지구 표면 우클릭 메뉴로 사용자 단말(UT)·지상국(GS)을 각각 지정하면 지상 통신 모드로 전환합니다. 오른쪽 드래그 확대/축소는 유지합니다.
- 기본 6×12 및 72×22 Starlink S1 규모 프리셋. 설정 수정 후 성좌 적용.
- 재생·일시정지·초기화·배속·실험 구간 탐색(기본 24시간). 초기화는 설정한 실험 시작 UTC로 돌아갑니다.
- 성좌 적용은 시간·위성 선택·추적·통신 끝점·카메라를 초기화합니다. 잘못된 입력은 기존 성좌를 유지합니다.

## 모델과 한계

원형 2체 궤도. 기준 반지름 6,378,137m, 지구 중력상수 3.986004418e14 m³/s². 평균 운동으로 공전하고 GMST로 ECI → ECEF 변환합니다. 단위는 미터·초, 시각은 UTC. J2·대기 항력·실제 TLE·정밀 지구 자세는 미포함입니다. 설정 고도는 구형 기준이며 패널은 WGS84 타원체 고도이므로 약간 다릅니다.

통신망은 **고정 논리 메시 + 지구 차폐 검사**이며 라우팅은 BFS·수동 후보·자동 우세 경로·MCSR 검증 모드입니다. 같은 궤도 앞뒤 위성 및 인접 궤도의 동일 슬롯을 연결하며 첫·끝 궤도 seam은 연결하지 않습니다. 지표 위 1km 여유를 둔 구형 차폐를 적용합니다. 동방향 최근접 ISL·핸드오버 규칙, 자동 SRD 분할·DS 선출, 패킷 큐·혼잡·대역폭·손실은 아직 적용하지 않았습니다.

링크 가용 상태는 시뮬레이션 시간 1초 간격으로 평가합니다. 패킷 점은 시뮬레이션 16초에 경로를 통과하는 관찰용 표시이며 실제 통신 시간·처리량과 무관합니다. 경로 변경 시 점은 새 경로로 전환합니다. 위성은 멀리서 점으로, 카메라와 위성 간 거리 5,000km 이내에서는 로컬 위성 PNG로 표시합니다. 이미지는 화면을 향하는 아이콘이며 실제 크기·자세를 가진 3D 위성 모델은 아닙니다. 궤도선은 궤도당 하나로 표시합니다. 전체 궤도선은 기본 숨김입니다.

## 지상 통신: GS → UT

지구 표면 우클릭 → GS 또는 UT 지정. 오른쪽 패널의 통신 끝점에서 기존 위성↔위성 모드로 돌아갈 수 있습니다. 지상 모드의 전체 보기는 GS(미지정이면 UT)를 지구본 정면에 둡니다. 지상 좌표는 패널에서 수정·삭제할 수 있고, 위치·접속 설정 적용은 시작 UTC부터 **새 실험**을 만듭니다. 자동 핸드오버는 실행 중 시계·CSIB·장애 일정·지표를 유지합니다. `지상 통신 예제 · 72기`는 멕시코시티 GS와 로스앤젤레스 UT의 10분 입력입니다. 기본 BFS이며 같은 입력에서 MCSR로 바꿔 비교할 수 있습니다. CLI에서도 `npm.cmd run simulate -- examples/ground-72.json`으로 재생합니다.

지상 모드는 GS 1개·UT 1개를 지원하고 경로는 `GS → 접속 위성 → BFS/MCSR의 ISL 경로 → 출구 위성 → UT`입니다. 같은 위성에 양 끝점이 접속하면 ISL 0홉이어도 정상 통신입니다. 지상 노드는 SRD에 포함하지 않으며 수동 고정 후보 모드는 위성 끝점에서만 지원합니다. 72기·1,584기 모두 같은 지상 접속 모델을 사용합니다. 지상 표식·접속선·노란 흐름을 표시하며 흐름 점은 기존과 동일한 관찰용 애니메이션입니다.

- 접속 가능한 위성은 구형 지구의 지표 법선 기준 **최소 고각 이상**인 위성입니다. 기본 최소 고각 10°는 실험 가정이며 실제 서비스 규격이 아닙니다. 1초 논리 기하 갱신과 접속 전환 완료 사건에서 평가합니다. 범위 밖 위성에 억지로 연결하지 않습니다. 72기에서는 지역·시각에 따라 미연결 구간이 발생할 수 있습니다.
- 최초에는 고각이 가장 높은 위성을 선택하고 동률이면 낮은 위성 번호를 선택합니다. 이후 현재 위성이 조건을 만족하는 동안 유지하고, 조건 이탈 때 다시 선택합니다. 접속 위성 선택은 ISL 경로 선택과 독립적이며 모든 접속 위성 조합을 최적화하지 않습니다.
- 0초의 초기 접속은 동기화된 상태로 시작합니다. 이후 획득·핸드오버는 기본 100ms의 구성 가능한 논리 전환 지연을 적용한 뒤 경로 계산·설치를 수행합니다. MCSR은 새 끝점의 필요한 영역 요약이 출발 영역에 도착하기까지 기다립니다. 끝점 변경 요청은 해당 DS에 즉시 반영하고 그 뒤의 요약·CSIB는 설정된 제어 전달로 전파합니다. CSIB를 전체 재초기화하거나 미완료 요약을 탐색 실패로 처리하지 않습니다.
- 종단 간 가용률·중단은 전체 논리 시간에서 측정합니다. 중단이 이어지는 동안 접속 불가 → 전환·경로 수립 → 위성망 경로 불가로 상태가 바뀌어도 서비스 중단은 한 건입니다. 상태별 시간은 우선순위에 따라 겹치지 않게 집계하며 물리적 근본 원인을 모두 추론한 결과는 아닙니다.
- 기존 위성망 복구 통계는 접속·끝점 전환 준비 구간을 제외한 `monitoredUs`에서 측정합니다. 진행 중 ISL 중단이 끝점 변경으로 관측 종료되면 `censored`로 기록하고 복구 평균·미복구 횟수에 섞지 않습니다. 종단 서비스 중단은 이와 별도로 계속 측정합니다.
- 종단 간 전파 지연은 지상 두 구간의 거리/c와 현재 ISL 전파 지연의 합입니다. 지상 거리·고각은 1초 표본이며 거리 1mm·고각 10⁻⁹도, 합산 지연 10⁻⁹ms 정밀도로 기록해 브라우저와 Node의 미세한 연산 차이를 줄입니다. 버퍼·지터 속성은 ISL 모델에만 적용합니다.

논리 좌표는 기존 궤도·차폐 모델과 같은 반지름 6,378,137m의 구형 지구, 지상 고도 0m입니다. 화면은 같은 위경도를 WGS84 타원체 위에 놓고 표식은 겹침을 피하려고 500m 높여 그립니다. 지형·건물 차폐, 전파 링크 버짓·날씨·빔/접속 용량, 실제 패킷 큐, 외부 지상망은 모델링하지 않습니다. 지상 가시성 인지는 평가 시점에 즉시 이뤄지며 접속 전환 지연은 실측 프로토콜 시간이 아닙니다. 모든 접속·핸드오버·라우팅·지표 계산은 Worker/CLI 논리 엔진이 담당하고 FPS는 결과를 바꾸지 않습니다.

## 실험 엔진

`SimulationEngine`은 정수 마이크로초 논리 시계와 사건 큐로 동작합니다. 사건은 시각 → 우선순위 → 등록 순서로 처리하며, 장애 명령 → 기하 갱신 → 최종 물리 링크 합성 → SLS → 계산 완료 → 경로 설치 순서입니다. 같은 시각의 입력을 합성한 뒤 링크 상태를 한 번 적용하며, 그 시각의 모든 사건이 끝난 후 서비스 가용성을 평가합니다. 브라우저에서는 전용 Web Worker가 실행하고 Cesium은 약 10Hz 진행 메시지 사이의 표시 시각을 매 프레임 보간합니다. 최초 전체 상태 이후에는 시각·연속 상태 리비전을 가진 변경분을 받으며, 링크·경로 상태는 변경 시각이 표시 시각 이하일 때만 적용합니다. 한 전송 구간 안의 단절과 복구도 각각 보존합니다. 표시는 일반 재생에서 약 100ms 늦을 수 있으며 수신한 논리 시각을 넘기지 않습니다. 위성·ISL·패킷은 같은 표시 시각을 사용합니다. 배속·GPU·FPS는 표시 속도에만 영향을 주며 처리할 사건을 건너뛰지 않습니다.

물리 링크와 라우터가 인지한 링크를 분리합니다. 기하 가용성은 절대 논리 시각 1초 간격으로 갱신하고, 예약 장애는 지정 마이크로초에 반영합니다. SLS는 실험 시작을 기준으로 일정한 간격이며 3회 연속 누락 시 장애를 인지합니다. 복구된 링크는 다음 SLS에서 인지합니다. 정상 링크의 성공 메시지 반복은 생략하고 변경 링크의 관측만 사건으로 실행합니다. 경로는 인지한 그래프에서 계산하며, 인지 상태·속성 입력 버전이 바뀌면 이전 계산·전환·설치 작업을 폐기합니다. 같은 논리 시각의 인지·속성 입력을 합친 뒤 라우팅 판단을 한 번 실행합니다.

기본값은 **SLS 100ms, 계산 지연 1ms, 설치 지연 1ms, 통지 지연 0ms, 예비 전환 지연 0ms**입니다. 이는 논문에서 검증한 수치가 아닌 실험용 가정입니다. 실제 BFS 실행 시간은 별도 `profiling.wallMs`에만 기록하며 논리 지연과 합산하지 않습니다. 시드는 시나리오에 보존하며 현재 무작위 장애 생성은 없습니다.

- 왼쪽 실험 패널: 시작 UTC·길이·SLS·계산/설치/통지/예비 전환 지연 설정, 다음 사건, 끝까지 실행, JSON 저장. 기본 시작 UTC는 **2026-01-01T00:00:00.000Z**이며 시드는 1의 예약값으로 표시합니다. 난수 생성은 미사용입니다.
- 오른쪽 ISL 장애 패널: 링크 선택, 즉시 장애/복구, 시각 예약, 서비스 중단 통계와 최근 6건, 별도의 링크 장애 이력.
- `linkFailures`: 링크별 물리 단절 `startedUs`, 물리 복구 `restoredUs`, 라우터 인지 `detectedUs`. 서비스 복구 시각을 링크의 물리 복구 시각으로 쓰지 않습니다.
- `serviceOutages`: 현재 출발→도착 한 쌍의 연속 비가용 구간입니다. 중단 중 추가 링크가 끊겨도 한 건으로 유지합니다. 관련 링크는 해당 구간의 설치 경로 및 중단 시작 경로에서 실제로 단절된 링크만 누적하므로 네트워크 전체의 근본 원인 분석 결과는 아닙니다.
- 서비스 `recoveryUs`는 중단 시작부터 가용 경로 복구까지, `detectionUs`는 관련 장애를 처음 인지하기까지, `establishmentUs`는 그 인지부터 복구까지입니다. 인지 전 복구는 감지·수립 시간을 `null`로 기록합니다. 음수로 역산하지 않습니다.
- `outageCount`, `totalDowntimeUs`, `availability`, `meanOutageUs`, `recoveredCount`, `unrecoveredCount`, `pendingCount`, `initialOutageCount`를 제공합니다. 평균은 복구 완료 건만 포함하므로 미복구·진행 중 건수와 함께 해석해야 합니다.
- 측정 구간은 **[0, 현재 논리 시각)** 입니다. 초기 미연결도 0초부터 포함하고 현재까지 미복구인 시간도 누적합니다. 0초 가용률은 `null`, 출발=도착은 가용입니다. 정확히 종료 시각에 시작된 중단은 최종 상태와 이력에는 남지만 해당 구간 통계에는 아직 포함하지 않습니다.
- 뒤로 탐색하면 원본 시나리오와 장애 일정을 처음부터 재실행합니다. 성좌·통신 끝점·실험 설정 변경은 새 실험으로 시작하며 장애 일정을 초기화합니다.

전체 체크포인트는 실행 중 벽시계 5초마다, 일시정지와 종료 때도 검증용으로 전송합니다. 변경분 누락·불일치 또는 표시 버퍼 8,192건 초과 시 현재 전체 상태로 재동기화합니다. 소비한 표시 변경분은 폐기합니다. 재동기화·탐색·단계 실행은 현재 논리 시각에 맞춰 표시를 재설정합니다. 화면의 지연은 지표 계산에 포함하지 않습니다.

새 시나리오는 `schemaVersion: 9`, 결과는 `modelVersion: "mcsr-ground-v9"`입니다. v9는 `ground`(위성 모드면 `null`)와 `mcsrSearch`를 필수로 저장합니다. 무버전·v1~v8 파일은 입력 UTC·시드·일정과 기존 라우팅 설정을 보존해 v9의 위성 모드로 읽습니다. v8의 탐색 설정은 그대로 보존하고 v7 이하는 `reference`로 유지합니다. 예전 대규모 BFS 파일을 자동으로 제한 탐색 실험으로 바꾸지 않습니다. v6 이전의 누락된 SRD는 성좌 범위 내 2×2로 채우고, v7 이전의 제어 전달은 `fixed`로 보존합니다. v7의 ISL/ACK 설정은 그대로 보존합니다. 새 파일의 제어 전달 기본은 `isl`, ACK 제한 1초입니다. 지원하지 않는 버전·잘못된 설정은 현재 실험을 변경하지 않고 거부하며 기존 파일을 덮어쓰지 않습니다.

저장한 **시나리오 JSON**은 같은 코어로 화면 없이 재생할 수 있습니다. 결과 저장 JSON에는 시나리오·논리 결과·사건 로그·실행 시간 프로파일이 포함됩니다.

```powershell
npm.cmd run simulate -- .\mcsr-scenario.json
```

패킷 점은 시각화만 수행합니다. 패킷별 전달 지연·손실률·큐 동작·직렬화 지연은 아직 측정하지 않습니다. 전파 지연은 위성 간 거리로 계산한 이론값입니다. BFS는 비교 기준선이며 MCSR 모드도 실제 패킷의 전달·손실을 측정하지 않습니다.

## 다중 속성 링크 모델

라우팅 입력은 전체 노드 수와 `NetworkLink[]`로 구성합니다. 각 링크는 인지된 연결 상태(`knownAvailable`)와 D/A/J를 제공하며, 아직 감지하지 못한 물리 장애 정보는 전략에 전달하지 않습니다. 현재 무방향 링크의 양방향에 같은 속성을 적용합니다.

- **D**: 논리 시각의 위성 간 거리(m) ÷ 299,792,458 × 1,000으로 계산한 전파 지연(ms). 플랫폼 수학 함수의 미세 오차가 선택을 바꾸지 않도록 1ps(0.000000001ms) 단위로 정규화합니다.
- **A**: `(bufferCapacityPackets - queuedPackets) / bufferCapacityPackets`. 기본 큐 용량 1,000개, 점유 0개로 A=1입니다. 대역폭·처리량이 아닙니다.
- **J**: 비음수 가상 입력(ms), 기본 0. 패킷 도착 시각에서 측정한 값이 아닙니다.

시나리오 JSON의 `linkMetricUpdates`에 링크별 초기값과 변경을 입력하고 CLI로 재생할 수 있습니다. 화면의 **시나리오 가져오기**로 같은 JSON을 3D에서 재생할 수 있습니다. 결과 저장 JSON의 scenario도 가져옵니다. 잘못된 파일은 현재 실험을 유지하며, 가져오기는 일시정지된 0초에서 시작합니다. 파일 크기는 10MB 이하입니다. 대규모 결과 JSON은 이 한도를 넘을 수 있으므로 재생용으로는 별도의 **시나리오 저장** 파일을 사용하세요. 결과 저장은 크기를 줄이기 위해 공백을 생략하며 데이터 내용은 유지합니다. 속성 일정의 직접 편집은 JSON으로 수행합니다. 다음은 **시나리오의 일부**입니다. 저장한 시나리오에 추가하세요.

```json
"linkMetricUpdates": [
  { "atUs": 0, "linkId": "0:1", "bufferCapacityPackets": 1000, "queuedPackets": 800, "jitterMs": 2 },
  { "atUs": 500000, "linkId": "0:1", "bufferCapacityPackets": 1000, "queuedPackets": 950, "jitterMs": 5 }
]
```

각 변경은 모든 큐·지터 값을 지정하며 다음 변경까지 유지됩니다. 시각은 정수 마이크로초, 용량·점유는 정수 패킷 수입니다. 같은 시각·링크의 중복, 없는 링크, 실험 범위 밖 시각, 용량 초과 점유, 음수·비유한 지터는 거부합니다. 속성은 지정 시각에 즉시 알려진다고 가정하며 속성 광고 지연은 모델링하지 않습니다. 난수·렌더링 FPS·현재 시스템 시각을 입력으로 사용하지 않습니다.

`RoutingStrategy.calculate(graph, source, target)`의 반환값은 엔진이 독립적으로 검증합니다. 출발/도착·정수 노드 범위·중복 노드/순환·인지된 링크 연속성·D/A/J 재계산 일치를 검사하며, 잘못된 결과는 오류로 중단합니다. 수치 비교 오차는 1e-9 × max(1, 절댓값)이며 실제 값은 재계산한 값으로 저장합니다. 같은 노드열의 중복 후보는 합치고, 속성이 같아도 서로 다른 경로는 유지합니다. 전략에는 원본 입력의 복사본을 전달해 입력을 바꿔 검증을 우회할 수 없게 합니다.

시나리오의 `routing`은 BFS·수동 후보·자동 우세 경로 모드를 지원합니다.

```json
"routing": {
  "algorithm": "candidate-paths",
  "service": "TS",
  "candidatePaths": [[0,1,2,3], [0,7,6,5,4,3]]
},
"notificationDelayUs": 10000,
"switchDelayUs": 0
```

`bfs`는 기존 최단 홉·동률 순서를 유지하며 LS/TS에서는 속성만 바뀌면 재계산하지 않습니다. HR에서는 지터 제한의 충족 여부가 바뀔 수 있으므로 속성 변경을 다시 평가합니다. `candidate-paths`는 명시된 경로를 평가하며 속성 변경과 유의미한 기하 지연 변경에 반응합니다. `source`/`target` 또는 성좌를 화면에서 변경하면 새 BFS 실험으로 초기화합니다. 알고리즘·서비스 변경은 현재 일정과 설정을 보존한 새 실험으로 시작합니다. 코드에서 주입하는 임의의 JavaScript 전략은 테스트용이며, 재생 가능한 제품 알고리즘은 `createRoutingStrategy`에 등록하고 시나리오 식별자로 복원합니다.

후보를 비교할 때 D·J는 작고 A는 큰 쪽이 우세합니다. 모든 속성에서 나쁘지 않고 하나 이상에서 더 좋은 후보가 있으면 해당 후보는 선택에서 제외하지만, 장애 시 사용할 수 있도록 계산된 후보 풀에는 남깁니다. LS는 D 최소 → A 최대 → J 최소, TS는 A 최대 → D 최소 → J 최소를 사용합니다. HR은 **J < 15ms** 후보에 대해 TS 순서를 적용합니다. 완전히 같은 값은 노드열 문자열 순서로 결정합니다. HR 규칙은 논문 본문의 필터·버퍼 우선 해석이며, 의사코드의 큰 J 선호를 재현하는 모드는 아닙니다.

인지된 링크 단절 시 완료된 계산의 후보 풀을 현재 그래프로 재검증합니다. 유효한 예비 후보가 있으면 **예비 전환 지연 + 설치 지연**만 적용하고 재계산하지 않습니다. 기존 경로가 그대로 선택되면 유지 사건을 기록합니다. 예비 후보가 없거나 링크가 복구되면 새로 계산합니다. 속성 변경은 후보를 새로 계산·선택합니다. 계산이 논리적으로 완료되기 전인 후보는 예비 풀로 공개하지 않습니다. 기존 전역 인지 모드의 감지 후 통지는 별도 지연 사건이며, 전달 전에 물리 상태가 바뀌면 오래된 통지를 취소합니다. MCSR의 ISL 모드는 아래 제어 메시지 전달 규칙을 사용합니다.

`routingAnalyses`는 입력 버전·시각·서비스·선택/제외 이유·우세 후보·재계산/예비 재사용 모드와 대기/설치/유지/폐기 상태를 기록합니다. `routingEvaluations`는 실제 계산 호출, `installedEvaluation`은 설치 후보의 계산 당시 속성, `currentPathMetrics`는 현재 논리 시각의 경로 속성입니다. 출발=도착은 `(0,1,0)`, 경로 부재/물리 단절은 현재 평가 null입니다. 화면의 경로 후보를 누르면 파란 검토 선으로 표시하며, 설치된 녹색/빨간 경로와 구분합니다. 후보 상태는 논리 시각 기준이고, 3D의 링크/설치 경로는 표시 시각 기준입니다. 판단 변경분과 상태 전이는 시간 정보를 가진 스트림으로도 보존합니다.

사건 로그는 감지 → 통지 시작/완료 → 후보 판단 → 재계산 또는 예비 전환 → 설치 시작/완료를 구분합니다. `delayModel`은 설정값을 결과에 남기며, CPU 실행 시간은 `profiling`에만 기록합니다. BFS·수동 후보·자동 우세 경로는 전역 인지 모델을 사용합니다. MCSR은 영역별 인지 및 DS·CSIB 수신 시각을 따로 관리하고 제어 메시지에 실제 가용 링크와 기하학적 전파 지연을 적용합니다. 큐·직렬화·대역폭 경쟁이 포함된 실제 패킷 모델은 아닙니다. 전체 링크 속성을 매 진행 메시지에 싣지 않습니다.

예제 `examples/candidate-routing.json`을 화면에서 가져오거나 다음 명령으로 실행하세요. 0.5초의 버퍼 변화에 TS 경로가 바뀌고, 1초의 장애 후 저장된 다른 후보로 전환합니다. 같은 시나리오에서 LS와 TS를 바꾸면 선택 차이를 확인할 수 있습니다.

```powershell
npm.cmd run simulate -- .\examples\candidate-routing.json
```

수동 후보와 자동 우세 경로는 비교·진단용입니다. MCSR 영역별 동작은 아래 별도 모드에서 검증합니다. 모든 모드에서 실제 처리량·손실률·실측 지터는 측정하지 않습니다.


## 자동 우세 경로 · 검증용

`routing.algorithm`을 `dominant-paths`로 지정하면 후보 노드열을 입력하지 않아도 인지된 그래프에서 우세 경로를 생성합니다. `candidatePaths`는 빈 배열로 지정합니다. 동일한 그래프에서는 LS/TS/HR와 관계없이 같은 후보 집합을 만들고, 서비스 선택은 그다음에 적용합니다.

노드 번호순 깊이 우선 탐색으로 순환 없는 모든 단순 경로를 확인하고, 목적지에서 D/J 최소·A 최대 기준으로 지배 관계를 비교합니다. 중간 노드의 속성만으로 경로를 제거하지 않습니다. 같은 속성의 서로 다른 경로는 예비 경로로 유지합니다. 이 구현은 MCSR 경로 계산의 정답을 검증하고 SRD 계산에 연결하기 위한 작은 그래프 참조 구현이며, 논문의 SRD 기반 Algorithm 2·3 자체를 구현한 것은 아닙니다.

자동 모드의 지원 한도는 **전체 노드 16개, 한 계산당 경로 확장 100,000회, 보존 후보 2,048개**입니다. 16기 초과 시 화면 선택과 JSON 입력을 차단합니다. 탐색·후보 한도 초과는 부분 후보를 반환하거나 BFS로 바꾸지 않고 계산 전체를 실패 처리합니다. 실패한 엔진은 진행할 수 없고, Worker는 재생을 중단해 ‘계산 실패’를 표시합니다. 런타임 실패 결과는 `completed:false`, `validForAnalysis:false`, `failure`의 시각·코드·이유·미완료 탐색 요약을 기록합니다. 초기화 실패로 프레임이 없으면 결과 저장을 비활성화합니다. 초기 탐색을 포함해 진단 프레임이 남은 실패는 분석 불가 상태와 실패 이유를 저장할 수 있습니다. CLI 실패는 종료 코드가 0이 아니며 성공 JSON을 출력하지 않습니다.

전략의 선택적인 네 번째 인자 `reportSearch(summary)`로 완료된 검색 요약을 전달합니다. 완료되지 않은 요약은 엔진이 거부합니다.

실제 검색이 실행된 `routingEvaluations.search`와 `routingAnalyses.search`에는 확장 횟수·완성 경로 수·최종 후보 수·제거 수와 최대 20건의 제거 사례를 기록합니다. 화면은 같은 요약과 제거 근거를 표시합니다. 제거 근거의 우세 경로는 비교 당시의 경로이며 이후 더 좋은 경로로 교체될 수 있습니다. 예비 전환은 검색하지 않으므로 해당 판단에는 새 검색 요약을 붙이지 않습니다. 전체 탐색 상태나 모든 제거 경로를 전송하지 않습니다.

`examples/dominant-routing.json`을 가져오면 8기 성좌에서 자동 후보 2개를 확인할 수 있습니다. 0.5초 버퍼 변경으로 TS 경로가 바뀌고, 1초 주 경로 장애는 저장된 후보로 전환합니다. 2초에 남은 경로도 끊기면 예비 경로가 없어 다시 계산하고 경로 부재를 기록합니다. 서비스·시간을 바꾸거나 후보를 클릭해 기존 3D 검토 기능으로 관찰하세요.

```powershell
npm.cmd run simulate -- .\examples\dominant-routing.json
```

## MCSR · 소규모 정밀 검증 모드

화면의 **MCSR 예제 불러오기 · 16기**를 누르거나 `examples/mcsr-routing.json`을 가져오세요. 위성 2×8기, SRD 크기 1×4로 영역 네 개를 구성합니다. LEO에서 궤도당 4기는 위성 간 각도 90°로 고리 링크가 지구에 가려지므로, 4×4 대신 실제 가시 링크로 경로를 만들 수 있는 2×8 구성을 사용합니다. 이 예제의 극궤도 교차점에는 궤도 모델상 같은 위치에 있는 노드가 있으며 실제 충돌 회피·위성 배치 모델을 뜻하지 않습니다.

```powershell
npm.cmd run simulate -- .\examples\mcsr-routing.json
```

- `routing.algorithm:"mcsr"`, `srd:{planesPerDomain:1,satellitesPerDomain:4}`로 선택합니다. 영역은 논리 궤도면/슬롯으로 고정하며 나머지 노드는 마지막 작은 영역에 포함합니다. 경계 노드는 다른 영역으로 향하는 구조적 링크를 가진 노드이며 물리 단절로 역할이 변하지 않습니다. DS는 각 영역의 최대 좌표 노드로 고정합니다.
- 각 영역은 내부·인접 링크만 관측합니다. DS는 내부 경로(실제 노드열·홉 속성)와 경계 링크를 요약해 전달하고, 각 수신 영역의 CSIB는 마지막 수신 버전을 보관합니다. 실험 0초는 동기화된 초기 상태입니다. 이후 출발 영역의 로컬 정보와 수신 CSIB만 라우팅에 사용하며 물리 장애를 미리 조회하지 않습니다. MCSR의 기하 D는 가시성과 같은 1초 격자에서 관측하고, 버퍼·지터는 지정 시각에 반영합니다. 패널의 현재 물리 경로 D와 계산 당시 인지 D는 서로 다른 시점일 수 있습니다.
- 내부 단순 경로를 만들고 경계 입출구를 연결해 종단 후보를 생성합니다. 중간 속성 비교로 다른 예비 경로를 잃지 않도록 내부 변형을 보존하고 종단에서 비지배 집합을 구합니다. 같은 SRD의 다른 노드로 재진입은 허용하되 노드 재방문은 금지합니다. 이는 정확성 우선의 소규모 구현 규칙이며 논문 의사코드 직역이나 대규모 최적화 구현이 아닙니다.
- 새 ISL 모드는 DS 간 통지·ACK를 실제 링크를 따라 전달합니다. 이전의 직접 전달은 `controlTransport.mode:"fixed"`로 유지합니다. SLS 감지와 해당 영역 내부 반영은 분리해 기록하며 내부 반영에는 추가 지연을 두지 않습니다. 영역 내부 개별 노드 간 제어 전파는 모델링하지 않습니다.
- 입력은 수신 버전으로 관리하고, 알려진 연결 성분에 영향을 주는 변화에만 출발 서비스 판단을 갱신합니다. 저장 후보 전환에는 새 탐색 요약을 붙이지 않습니다. 최신 상태에서 재계산한 후보는 검증 전용으로 보관한 관측 그래프의 기준 탐색과 비교하며 불일치는 실패 처리합니다. CSIB 복원 과정이 링크를 누락해도 같은 오류를 정답으로 인정하지 않으며, 검증 그래프는 경로 생성에 사용하지 않습니다. 정보 전달 중에는 최신 물리 상태와의 후보 비교를 보류합니다.
- `routingAnalyses.mcsr`는 후보의 영역별 구간·의존 버전·동기화 여부·기준 비교를, 결과의 `mcsr.events`는 전체 CSIB 갱신 이력, `mcsr.csibs`는 영역별 최종 수신 경로·홉 속성 스냅샷을 담습니다. 패널은 최신 24건을 보여주며 시각을 누르면 그 시점으로 재실행합니다. DS 라벨·영역 색상·보라색 경계 링크와 선택 후보의 영역별 구간을 표시하고 SRD 표시를 끌 수 있습니다.
- 전체 16기, 영역 내부 확장/저장 각각 100,000개, 종단 확장 100,000회·우세 후보 2,048개의 한도를 적용합니다. 비교 탐색의 한도도 적용되며 어느 단계든 초과하면 실패합니다. 한도가 허용하는 작은 그래프의 정확성 검증이 목적입니다.

기본 8초 예제는 원격 ISL 10:11이 1초에 끊어져 출발 영역에 장애 정보가 전달된 뒤 예비 전환합니다. 2초의 13:14 장애는 물리 분할과 통지 실패를 만들고, 3초의 10:11 복구 후 재계산으로 서비스가 복구됩니다. TS 선택을 관찰하기 위해 버퍼·지터의 초기 가상 값을 사용하고, 재전송을 관찰하기 위해 ACK 제한 시간은 예제에서 500ms로 지정합니다. 이전 4초 고정 지연 실험은 `examples/mcsr-fixed-routing.json`으로 유지합니다.

## MCSR · 72기·1,584기 확장 모드

왼쪽 **MCSR 예제 · 72기 / 1,584기** 버튼으로 일시정지된 10분 실험을 엽니다. 기본 성좌에서 알고리즘을 MCSR로 바꿔도 확장 모드를 사용할 수 있습니다. 출발·도착 변경, LS/TS/HR 선택, 예비 경로·사건 선택, 시간 탐색과 JSON 저장도 같은 코어로 동작합니다.

| 기본 설정 | 72기 | 1,584기 |
|---|---:|---:|
| 성좌 | 6×12 | 72×22 |
| SRD 크기(궤도면×슬롯) | 2×4 | 6×4 |
| SRD 수(마지막 작은 영역 포함) | 9 | 72 |
| 내부 노드 쌍 후보 / 경계 라벨 / 종단 후보 한도 | 4 / 16 / 8 | 4 / 16 / 8 |
| 탐색 확장 예산 | 200,000 | 2,000,000 |

확장 모드는 SRD의 경계 노드와 현재 서비스 끝점 사이의 경로만 요약합니다. D 최소·A 최대·J 최소의 세 정렬을 번갈아 후보를 보존하며 단일 가중치로 합치지 않습니다. 노드 순환을 막고, 목적지에서 비지배 후보를 추린 뒤 기존 서비스 규칙으로 선택합니다. 한도 때문에 제외된 경로가 있을 수 있으므로 **`coverage:"bounded"`, `allCandidatesGuaranteed:false`**를 화면과 결과에 남깁니다. `search.complete`는 제한 정책 아래 계산이 끝났다는 뜻입니다. 전체 경로 집합의 완전성이나 전역 최적성 증명이 아닙니다.

- `mcsrSearch`는 모드, 내부 후보·경계 라벨·종단 후보 수, 확장 예산, 기하 D 관측 주기, 속성/재선택 묶음, 상세 로그 보존량, 제어 사건 한도를 저장합니다. 고급 설정은 JSON에서 수정합니다. 확장 SRD는 최대 32기로 제한해 큰 영역의 초기 내부 탐색을 방지합니다.
- D의 라우팅 관측 기본은 실험 시작 기준 30초 격자이며 로컬 관측과 원격 발행에 같은 샘플을 씁니다. 가시성 검사는 계속 1초, 제어 홉 전파 시간은 실제 홉 출발 시각의 거리를 씁니다. A/J 갱신과 일반 CSIB 재선택은 최대 100ms 논리 격자로 묶습니다. 감지된 링크 단절·복구는 해당 로컬 반영 시점에 처리합니다. 수신 때 순수 단절만 바뀌면 즉시 저장 후보를 검토합니다. 이 주기는 성능 전용 옵션이 아니라 실험 결과에 영향을 주는 모델 설정입니다.
- 후보 요약과 별도로 모든 로컬 링크의 인지 상태를 보관합니다. 요약에서 빠진 경로를 링크 단절로 오인하지 않습니다. 경로를 못 찾으면 별도 연결성 검사로 실제 분리와 `bounded-no-candidate`를 구분합니다. 예산 초과·탐색 실패는 부분 후보를 설치하거나 BFS로 대체하지 않고 실패 처리합니다.
- DS는 ACK로 확인한 버전을 기준으로 링크·구간 변경분을 보냅니다. 기준 버전이 맞지 않으면 적용하지 않고 실제 역방향 제어 경로로 전체 상태를 요청합니다. 요청이 발신자에 도착하면 새 시도로 전체 상태를 보내며, 적용하지 않은 변경분을 성공 ACK로 인정하지 않습니다. 같은 불변 요약·그래프·제어 BFS 트리는 재사용합니다.
- 종단 탐색은 256회 확장마다 Worker에 제어를 돌려주고 사건 처리도 묶음으로 실행합니다. 미완료 논리 시각의 결과는 전송·관측·성공 저장하지 않습니다. 일시정지는 진행 중인 논리 시각을 마친 뒤 표시하고, 새 불러오기·탐색은 이전 작업을 버립니다. 탐색·사건을 건너뛰지 않으며 CPU 활성 실행 시간만 별도 프로파일에 기록합니다.
- 화면에는 최초 SRD/토폴로지 이후 변경된 도메인·링크·비행 정보만 보냅니다. 상태 리비전 연속성과 주기적 체크포인트 검증은 유지합니다. DS 라벨은 실제 대표 위성에만 생성합니다. 영역이 많으면 멀리서는 출발·도착·선택 영역 이름표를, 확대하면 가까운 DS 이름표를 표시합니다. 긴 버전 목록은 접어 표시하고, 긴 후보 경로는 끝점·노드 수·SRD 순서로 요약합니다. 전체 노드열은 툴팁과 결과 JSON에 보존합니다. 데이터 경로·모든 위성·ISL은 표시하고, 제어 점은 출발 SRD 송수신 중 최대 256개를 표시합니다. 선택한 이력의 제어 경로는 따로 강조합니다. 화면 필터가 다른 메시지의 논리 처리와 통계를 생략하지 않습니다.
- 상세 CSIB/제어 로그는 기본 최근 10,000건, 생략 수는 `traceOmitted`에 기록합니다. 화면 이력은 그중 출발 SRD 제어 사건 최근 24건입니다. 전체 집계는 모든 사건을 반영하고 제어 처리 한도 기본은 50,000,000건입니다. 결과의 CSIB는 중복 광고 대신 광고 목록과 각 DS의 버전 참조를 저장합니다. 따라서 정밀 모드의 전체 이력·CSIB 객체 형식과 구분해야 합니다.
- `search`는 전역 확장·제한 제외·종단 지배 제거와 내부 요약의 확장/제한 제외 수, 제한 제외 이유 사례를 담습니다. 소규모 정밀 기준 비교가 확장 결과를 대신 생성하지 않습니다. 같은 작은 그래프에서 서비스 선택을 따로 대조하는 검증을 유지합니다.

`examples/mcsr-72.json`, `mcsr-1584.json`은 가용 버퍼·가상 지터 입력을 바꾸는 실험이며 `*-uniform.json`은 A=1/J=0인 비교 입력입니다. 원격 링크 장애·복원, 출발 노드 격리·재연결을 명시적으로 예약합니다. J는 실측이 아니며 혼잡도 실제 패킷 큐에서 발생한 값이 아닙니다.

```powershell
npm.cmd run simulate -- .\examples\mcsr-1584.json
npm.cmd run benchmark:mcsr
```

벤치마크는 네 입력을 각각 논리 600초 실행하고 `artifacts/mcsr-scale-benchmark.json`에 초기화·벽시계 시간, 전역 라우팅 활성 시간, 계산 횟수·최대 활성 계산 시간, 관측 메모리, 제어 집계와 복구 구간을 기록합니다. 해당 폴더는 Git에서 제외합니다. 실제 처리 속도는 장비와 입력에 따라 달라지며 300× 표시 배속을 실시간으로 보장하지 않습니다.

## ISL 제어 메시지 검증

MCSR 설정의 **제어 통지 모델**, **ACK 제한 시간**을 바꾼 뒤 **제어 통신 적용**을 누르면 새 실험을 시작합니다. 잘못된 설정은 현재 실험을 유지합니다. JSON 설정은 `controlTransport:{mode:"isl",ackTimeoutUs:1000000}`입니다. 이 설정은 MCSR에만 적용하며 BFS 등 기존 비교 모드는 그대로 동작합니다.

- DS는 자신의 CSIB로 BFS 제어 경로를 계산합니다. 경로는 발신 시점에 고정하며 물리 상태를 미리 조회하지 않습니다. 각 홉에서는 실제 가용 상태와 전송 도중의 단절 여부를 확인합니다. 출발 이후 끊겼다가 도착 전에 복구된 링크도 해당 시도의 전달 실패로 기록합니다.
- `notificationDelayUs`는 갱신 메시지와 ACK 각각의 발신 처리 지연입니다. 경로는 이 처리 후의 인지 그래프에서 구합니다. 홉 지연은 출발 시점의 위성 간 거리에서 계산하고 정수 µs로 올림하며 최소 1µs입니다. MCSR 라우팅용 기하 속성은 기존 1초 관측 격자이고, 제어 메시지의 전파 시간은 각 홉 출발 시각의 기하를 사용합니다.
- 수신 DS는 새 버전을 적용한 뒤 자기 CSIB로 ACK 경로를 계산합니다. ACK가 도착해야 발신자의 해당 대기가 해제됩니다. ACK는 서비스 경로 설치를 기다리지 않으며 서비스 복구 시간에 합산하지 않습니다.
- ACK 제한 시간은 최초 발신 처리부터 왕복에 적용합니다. 기한 내 ACK가 없으면 최신 버전을 새 경로로 재전송합니다. 새 갱신은 이전 대기를 교체하지만 이미 이동 중인 이전 메시지는 자동 취소하지 않습니다. 중복·이전 버전은 상태를 덮어쓰지 않고 ACK를 반환하며, 이전 시도 ACK는 최신 대기를 완료하지 않습니다. 메시지는 자기 시도의 기한 뒤에는 수신자를 변경할 수 없습니다.
- 같은 논리 시각에는 물리 상태 확정→감지·로컬 반영→제어 메시지 도착→시간초과→서비스 경로 판단 순서입니다. 정확히 제한 시각에 도착한 ACK는 시간초과보다 먼저 처리합니다. 정밀 모드 제어 사건은 실험당 100,000건으로 제한하고 초과 시 `control-event-limit`, `validForAnalysis:false`, `completed:false`를 기록합니다.
- 결과의 `mcsr.control`에 전체 메시지 사건·ACK 대기·전송 중 메시지·통계를 저장합니다. `deliveredUpdates`는 중복을 포함한 수신, `appliedUpdates`는 실제 갱신, `deliveredAcks`는 이전 ACK를 포함한 수신, `acknowledged`는 유효한 대기 해제입니다. 측정 구간 끝에 진행 중인 통지나 ACK가 남을 수 있으며 `completed`는 측정 구간 완료를 뜻합니다.
- `serviceOutages.detectedUs`는 관련 링크 끝점에서의 감지, `sourceInformedUs`는 출발 영역이 해당 장애 정보를 인지한 시각입니다. 상대 지표 `sourceNotificationUs`, `informedEstablishmentUs`는 각각 중단→출발 인지, 출발 인지→복구입니다. `recoveryMechanism`은 `reserve`, `recalculate`, `physical-restoration`으로 서비스 재개 방식을 구분합니다. 설치 직전에 기존 경로가 비가용이고 새 설치로 가용해졌다면 원래 경로의 재설치도 재계산/예비 전환입니다. 물리 복원으로 기존 설치 경로가 이미 가용해진 경우는 물리 복구이며, 인지 전에 복구하면 인지 지표는 null입니다.
- 화면의 청록색 점은 CSIB 갱신, 보라색 점은 ACK, 주황색 선은 선택한 제어 경로입니다. 제어 메시지는 표시 시각의 상태·홉 출발/도착 시각으로 그리며 렌더링 FPS가 전달 결과를 바꾸지 않습니다. 최근 24건에서 사건을 선택하면 해당 시각과 실패 링크·수신 DS를 확인합니다.

초기 CSIB는 동기화된 상태로 시작합니다. DS 장애·선출, 초기 발견, 실제 패킷 큐·직렬화·대역폭 경쟁은 이 모델에 포함하지 않습니다. 제어 통지 실패와 네트워크 분할은 정상 실험 결과이며 엔진 오류와 구분합니다.

## Docker로 상시 실행

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\docker-up.ps1
```

같은 망의 다른 기기에서는 **http://<이 PC의 현재 LAN IPv4>:5174**로 접속합니다. 현재 주소는 **http://192.168.1.72:5174**입니다. PC의 IP가 DHCP 등으로 바뀌면 **변경된 IP:5174**를 사용하면 됩니다. Compose와 Windows 전달 규칙 모두 특정 PC IP 대신 `0.0.0.0`에 바인딩합니다. **http://localhost:5174**와 이전 **5714** 포트도 유지하며, 두 포트에 대한 Windows 방화벽 규칙은 같은 서브넷의 TCP 접속만 허용합니다.

`docker-up.ps1`은 빌드 후 `docker-lan.ps1`을 실행합니다. Windows 방화벽 및 WSL 포트 전달 설정에는 관리자 권한이 필요해 UAC 승인이 표시될 수 있습니다. 일반 Docker CLI 환경에서는 방화벽만 설정하며, 이 PC의 WSL Ubuntu 환경에서는 Windows 5174/5714 → WSL의 같은 포트 전달도 구성합니다. 기존의 다른 포트 전달 규칙은 수정하지 않습니다.

WSL 재시작으로 내부 IP가 바뀌었을 때는 재빌드 없이 다음 명령으로 전달 주소를 갱신합니다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\docker-lan.ps1 -Wsl
```

터미널을 닫아도 실행됩니다. Node 24 컨테이너에서 소스를 빌드한 뒤 Nginx 컨테이너가 정적 파일을 제공합니다. 코드 수정 후 `docker-up.ps1`을 다시 실행하면 새 버전으로 교체합니다. 첫 빌드에는 이미지·npm 다운로드를 위한 인터넷이 필요합니다. 시뮬레이션은 접속한 각 기기의 브라우저에서 독립적으로 실행하며, 여러 기기의 상태를 공유하지 않습니다.

일반 Docker CLI가 설치된 환경에서는 `docker compose up -d --build`로도 실행할 수 있습니다. 이 PC는 Docker가 WSL Ubuntu에 있고 O: 클라우드 드라이브는 WSL에서 직접 보이지 않으므로, 위 PowerShell 스크립트가 필요한 파일만 C: 임시 폴더에 복사해 빌드합니다. 컨테이너 실행에는 해당 폴더나 O: 드라이브 마운트가 필요하지 않습니다.

컨테이너는 `restart: unless-stopped`로 Docker 엔진 재시작 후 복구됩니다. 수동으로 중지한 경우는 다시 시작하지 않습니다. WSL 환경 상태와 중지는 다음 명령을 사용하세요.

```powershell
wsl -d Ubuntu --cd / --exec docker ps --filter label=com.docker.compose.project=mcsr-sim
wsl -d Ubuntu --cd / --exec docker stop mcsr-sim-web-1
wsl -d Ubuntu --cd / --exec docker start mcsr-sim-web-1
```

### 이 PC의 로그인 자동 실행

현재 사용자 예약 작업 `MCSR-Sim-WSL`을 등록했습니다. 로그인 시 숨김 PowerShell로 WSL Ubuntu를 시작하고 유지합니다. Ubuntu의 Docker 서비스는 기존에 systemd 자동 시작으로 설정되어 있으며, MCSR 컨테이너는 재시작 정책으로 복구됩니다. O: 드라이브가 아직 마운트되지 않아도 기존 이미지 실행은 가능합니다. Windows 로그인 전의 서비스 가용성은 보장하지 않습니다.

```powershell
Get-ScheduledTask -TaskName MCSR-Sim-WSL
```

자동 실행을 끄려면 다음 명령을 사용하세요. 컨테이너 자체 중지는 별도로 `docker stop`을 사용합니다. 다른 WSL 작업에 영향을 주는 `wsl --shutdown`은 사용하지 마세요.

```powershell
Disable-ScheduledTask -TaskName MCSR-Sim-WSL
Stop-ScheduledTask -TaskName MCSR-Sim-WSL
```

직접 컨테이너를 중지하면 `unless-stopped` 정책상 다음 Docker 시작에도 자동 복구되지 않으므로, 다시 제공하려면 `docker start` 또는 `docker-up.ps1`을 실행하세요.

## 성능 측정과 논리 결과 회귀 검사

성능 설정은 시나리오의 일부가 아닙니다. 기존 schemaVersion 9와 논리 시각·이벤트 우선순위·MCSR 탐색 제한을 유지하며, 실행 시간은 `performance.now()`로 별도 수집합니다. 벤치마크는 결과 디렉터리를 새로 만들고 전체 논리 결과의 SHA-256 및 압축 JSON을 보존합니다. 기존 측정 파일을 덮어쓰지 않습니다.

```powershell
# 네 가지 기존 입력을 30/60초로 절단하고 각각 3회 측정
npm.cmd run benchmark:mcsr -- --seconds 30,60 --repeat 3
# 30/60초에 시작된 CSIB 전파까지 관찰하는 진단 구간
npm.cmd run benchmark:mcsr -- --seconds 31,61 .\examples\mcsr-1584.json
# 전체 600초: 기본 명령도 계속 지원
npm.cmd run benchmark:mcsr -- .\examples\mcsr-1584.json
# CLI에서 화면 변경분 생성 비용을 제외한 실행
npm.cmd run benchmark:mcsr -- --render off --seconds 31 .\examples\mcsr-1584.json
# 계측 오버헤드는 같은 입력의 off/light/detail 결과를 따로 측정해 비교
npm.cmd run benchmark:mcsr -- --profile light --seconds 31 .\examples\mcsr-1584.json
npm.cmd run benchmark:mcsr -- --profile detail --seconds 31 .\examples\mcsr-1584.json
# 입력 해시가 같은 실험의 전체 논리 결과 일치 확인 및 실행 시간 비교
npm.cmd run benchmark:compare -- artifacts/performance/before artifacts/performance/after
```

`--output`으로 새 결과 디렉터리, `--budget`으로 호출당 사건 예산을 지정할 수 있습니다. 기준 소스를 별도 디렉터리에 보존했다면 `--engine <보존한-src/engine.ts>`로 같은 측정 도구에서 실행합니다. 짧은 실험은 종료 시각 뒤의 장애·속성 입력만 제외합니다. 종료 직전 송신된 제어 메시지를 강제로 완료시키지 않습니다.

`report.json`에는 생성자·진행·결과 생성·JSON 직렬화 시간, 기존 activeRoutingMs, 계산 횟수, 입력/결과 해시, Node/V8/CPU/커밋/옵션이 들어갑니다. 메모리는 생성자·진행 묶음·내보내기에서 관측한 **sampledPeakHeapBytes**, 최종 heapUsed, 프로세스 생애 최대 RSS를 구분합니다. sampled peak는 GC 사이의 실제 최고 heap을 보장하지 않습니다. wallMs는 압축·디스크 저장 시간을 제외합니다. 여러 입력을 같은 프로세스에서 순차 실행하므로 이전 입력의 GC와 JIT 영향도 있습니다.

`--profile light`는 SRD 내부 세그먼트, 라우팅 작업 slice, CSIB 갱신/적용/delta, 제어 생성/전달/ACK/재시도, 화면 변경분 생성 시간을 측정합니다. 각 scope의 inclusiveMs는 하위 작업을 포함하고 exclusiveMs는 하위 작업 시간을 제외합니다. 서로 중첩되는 inclusive 값을 합산하지 마세요. detail은 큐 push/pop과 나머지 사건 callback까지 측정하므로 짧은 진단용입니다. 이벤트 큐 처리 사건 수·최대 길이와 제어 기록 수는 별개입니다. globalSlice는 협력 실행 작업과 검증을 포함하며, 순수 전역 탐색 시간으로 해석하지 않습니다. CPU 프로파일은 Node의 `--cpu-prof`로 별도 수집할 수 있습니다.

브라우저는 `http://localhost:5174/?profile=light`로 열면 `window.__mcsrPerformance`에 Worker와 Cesium 지표를 보관합니다. 결과 JSON의 바깥쪽 performance에도 Worker 진단이 포함되며, scenario/result에는 들어가지 않습니다. FPS·프레임 간격 p95·JS 갱신 p95·렌더 제출 p95를 구분하며, 렌더 제출 시간은 GPU 완료 시간이 아닙니다. Worker의 eventsPerActiveSecond는 engine.counters의 events.executed와 activeMs로 계산하며, 생성자 시간 constructorMs는 별도입니다.

```powershell
# npm run dev 실행 후, 고정된 1440×1000 화면에서 72/1,584기를 각각 8초 관찰한 뒤 31초 Worker 끝까지 실행과 Headless 결과 일치 검사
npm.cmd run benchmark:browser -- "http://127.0.0.1:5173/"
```

브라우저 비교는 기본 off로 실행하고 `?profile=light` 진단은 별도 실행합니다. 1,584기 전체 ISL의 낮은 FPS와 동기 SRD 작업은 아직 개선이 더 필요합니다.

Worker는 일반 재생 6ms·끝까지 계산 12ms의 시간 예산 내에서 128건씩 처리하며, 전역 탐색은 64개 label 확장마다 제어권을 돌려줍니다. 이 값은 논리 지연에 적용되지 않습니다. SRD 내부 요약 생성은 아직 동기 작업이므로 한 번의 callback이 예산보다 오래 걸릴 수 있습니다. 취소·교체는 다음 제어권 반환 시 처리하며, 열린 논리 시각은 완료 결과로 내보내지 않습니다.

이번 범위는 성능 계측·핵심 최적화·정확성 회귀 검사입니다. BFS/MCSR 자동 비교 실행 및 비교 UI, 실제 패킷 큐/손실/처리량, DS 장애·재선출은 후속 작업입니다. 기존 `.github/workflows/ci.yml`의 테스트·빌드·브라우저 검증은 유지합니다. 성능 수치와 검증 범위는 [VALIDATION.md](VALIDATION.md)의 최신 기록을 참고하세요.


화면의 지상 통신 방향은 **송신 지상국(GS) → 위성망 → 목적지 사용자 단말(UT)**입니다. 요청에 따라 표시 명칭만 교환했으며, 기존 schemaVersion 9 파일과 결과를 유지하기 위해 JSON의 `ground.ut`는 송신측, `ground.gs`는 목적지 필드로 그대로 보존합니다. 우클릭 메뉴·좌표 입력·지도 라벨·접속 이력에는 교환한 명칭을 사용합니다.
